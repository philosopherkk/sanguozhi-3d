# 流動版計畫與量測基準

使用者要求「使網站適用手機」。本檔記錄**量測方法、已修項目、尚未處理項目**，
以便後續輪次能接上，而不是每次重新猜。

## 量測方法（可重現）

用 `agent-browser` 以 393×852（iPhone 14 Pro 視口）開 `vite preview`，再以
`eval` 讀取 `getBoundingClientRect()` 與 `getComputedStyle()`。所有下面列出的
數字都是這樣量出來的，不是推測。

注意：無頭環境無法模擬 `(pointer: coarse)`（`matchMedia` 回傳 false、
`ontouchstart` 不存在）。因此凡是需要在 CI 裡驗證的規則，一律放在**寬度斷點**，
不把關鍵行為綁在 `pointer` 查詢上。

## 改動前（基線）

| 區塊 | 高度 | 佔螢幕 |
|---|---|---|
| 頁頭 `app-header` | 192px | 23% |
| 朝代列 `era-bar`（18 按鈕換行） | 256px | 30% |
| 年份滑桿 `year-scrubber` | 144px | 17% |
| 地圖＋側欄 `app-shell__main` | **230px** | **27%** |

另外三項客觀缺陷：

1. **內容比視口寬 28px 且被剪掉**。`.app-shell` 寬 393px，但其單一隱式
   欄位解析為 `420.812px`——grid item 的 `min-width` 預設為 `auto`
   （即 min-content），被不可斷行內容撐開，再由 `overflow: hidden` 剪掉右側。
   後果：頁頭、朝代列、年份滑桿最右一列永遠不可見。
2. **全 repo 零個 `env(safe-area-inset-*)`**，且 `viewport` 無 `viewport-fit=cover`。
3. **29 個控件低於 44px**（`year-scrubber__tick` 13 個 25×22、`app-header__step`
   35×36、`map-2d__zoom-btn` 32×30 等），`body` 的 `touch-action` 為 `auto`。

## 修 9：流動版字級

`App.css` 的字級全部以桌面版為基準排，流動版原本只覆蓋其中兩項。
393×852 的實讀值：主要內文 13.6px、卡片內文 10.4px、出處引文 8.8–9.3px、
地圖省界標籤 9px。繁體宋體筆畫密，細字在行動裝置上最先糊掉，
10px 以下已低於可長時間閱讀的下限。

以 `--fs-prose`／`--fs-prose-2`／`--fs-ui`／`--fs-meta` 四級重排，全部用 `rem`，
所以 `ReadingControls` 的小／大（改 `html` 的 font-size 百分比）仍然可用，
兩者是相乘而非互斥。只調整字級與行距，不引入新字型、不改配色。

| 層級 | 改動前 | 改動後 |
|---|---|---|
| 主要內文（詳情窗、文章、人物摘要） | 13.6px | **18px** |
| 長篇意譯 `.event-detail__paraphrase--long` | 16.3px | 20px |
| 原文引用 `.event-detail__quote blockquote p` | 17.9px | 20.8px |
| 卡片內文（勢力、成語、年表） | 10.4–12.5px | 16px |
| 可點選文字（分頁、按鈕、朝代名） | 9.9–14.4px | 15px |
| 標籤・出處・註記 | 8.8–11.5px | 13–15px |
| 地圖標記（原本用 px，不受小／大影響） | 9–11px | 12–14px（改 rem） |

**刻意不放大**：`year-scrubber__tick-*`（三國時代 13 格密排，單格僅 25px 寬，
放大後年份互相重疊）、`.app-header__title`（已是 18.4px，再放大會把頁頭擠出多一列）。

**代價**：介面固定列 421→448px（頁頭 155→162、朝代列 56→62、滑桿 180→188、
頁尾 30→36），`app-shell__main` 432→**404px**（−28px，−6.5%）。
正文在可捲動面板內，故 18px 相比 17px 不再佔用額外固定高度。

**由放大字級引發、已修的兩個回退**：
1. `.app-header` 是 `flex-wrap: wrap`，控件變寬後多擠出一列，頁頭 155→185px，
   內容 406px > 容器 393px，正是結構閘門第 1 條那類爆框。收緊頁頭與控件間距、
   移除 `.app-header__year` 的 min/max-width、不給調字級按鈕 `min-width`
   （高度仍補到 `--tap-min`）→ 回復 393px，無溢出。
2. `--preview` 那行原本靠 `text-overflow: ellipsis` 截斷，字級放大後截得更早
   （可容納寬度 397→292px）。改交還使用者橫向拖完，與處理
   `.year-scrubber__note--press` 的做法一致。

**量測方式補記**：本輪在桌面分頁內掛一個 393×852 的**同網域 iframe** 載入應用，
media query 依 iframe 視口求值，故 `(max-width: 700px)` 的規則確實生效，
再以 `frameID` 讀 `getComputedStyle()`。用本檔既有數字校準：基線頁頭 155px、
朝代列 56px 與上表吻合。

## 修 10：平板字級（701–859px）

修 9 的所有規則都寫在 `@media (max-width: 700px)` 之內，平板因此完全沿用
`App.css` 的桌面字級。實測 768×1024（iPad 直式）：卡片內文 10.4px、
地圖省界 9px、標籤與出處 11.5px、年份備註 9.9px。平板的物理尺寸比手機大、
閱讀距離更遠，拿到的卻是全站最小的字，方向正好相反。

還有一個不是「字小」的問題：**三層意譯在平板失去層級**。逐字原文
（`--paraphrase--long`）與短篇意譯同為 13.12px，讀者無法分辨原文／意譯／白話，
而流動版是 20.8 > 20 > 18 三級分明。這說明桌面版並非「只是字小」，
而是這三個層級在該寬度根本塌成一級。

### 做法

1. **把 修 9 的媒體條件擴到 `701–859px`，沿用同一組選擇器**，不重寫一份清單。
   上限取 859px 是 `App.css` 自己「單欄／堆疊」版面的斷點（`App.css:41`、`295`），
   因此本區覆蓋的正是版面已經切到窄版的寬度；大於 859px 回到桌面兩欄，
   字級另計。沒有另發一個數字，也沒有用容器查詢。
2. **原本寫死的 rem 收為 token**（`--fs-long`／`--fs-quote`／`--fs-title`／
   `--fs-title-2`），預設值與原寫死值逐一相同，故流動版實測不變；
   平板再以 `:root` 覆寫。`:root` 特異度不變而位置較後，故只在平板生效。
   這樣平板只需改八個數值，不必重複上百行選擇器——兩份清單必然走樣。
3. **修 3（朝代列單行橫滑）同樣擴到 701–859px**：20 顆時代按鈕在 768px
   之下必然換行（實測 155px，字級放大後增至 182px，佔直式 iPad 近兩成），
   而橫滑的互動與觸控或指標無關。修 4／修 5 那種「收起標語、收起提示行」
   是以隱藏內容換空間，平板不需要，故留在 700px 以內。
4. **修 9.3 的頁頭外距收緊拆出為 9.3a**，只限 700px：那五條是外距而非字級，
   平板頁頭本來有空間，收緊反而擠壓品牌標題。

### 順帶修掉的一個流動版漏網之魚

全元素字級盤點（列出所有 computed < 11px 且有文字的元素）發現
`.side-rail__map-first`（「顯示地圖」按鈕）在手機上仍是 **10.4px**：
`App.css` 把它與 `.side-rail__toggle` 排進同一條 `font-size: 0.65rem`，
而 修 9.3 只列了後者。已補入，手機 10.4→15px。
**教訓**：`audit:mobile` 查的是結構不變量，查不出「某個 class 忘記列進清單」；
這種缺陷只能靠全元素盤點發現，下次改字級要重跑同一份盤點，不是只抽查幾個 class。

## 結構閘門 `npm run audit:mobile`

六條不變量，每條對應一個真實發生過、肉眼看不出的缺陷：
`blowout`、`mapside-stack`、`mobile-pager`、`safe-area`、`bare-vh`、`tap-min`。
（本檔先前寫「五條」，漏了 `mobile-pager`——文件落後於腳本，實跑是六條。）
附 `--teeth` 自我測試：把缺陷逐一注入記憶體中的 CSS，確認每條都會報紅。
本輪 `--teeth` 曾抓出自己兩個問題——第一版解析器找不到規則（全部報紅），
第二版 `tap-min` 的注入樣板改錯目標；兩者都是靠自我測試才現形。

## 簡體字閘門也會全綠地失明（`audit:chars`）

`audit:chars` 的字表是手工維護的，本檔上面已記過三次補表。這輪再用
**opencc 的 `s2t` 全量轉換**（逐字比對原文與轉換後文字，不同即疑）覆核一次，
查出四個從不在表裡的常見簡體字，並找到八處既存錯字——其中三處在使用者
看得到的資料內文：

| 字 | 正字 | 實例 |
|---|---|---|
| `扩` | 擴 | `earlyDynasty.ts`「宮城的扩建」、`timelineMore.ts`「扩展到州野」「扩張」 |
| `两` | 兩 | `edoPack.ts`「這兩層讀法」、`heian/data/history.ts`「两條東宮線」、`mobile.css` 註釋「两者」 |
| `刘` | 劉 | `mobile.css` 註釋「刘海」（應作「瀏海」） |
| `项` | 項 | 本檔舊表格標題「项目」 |

八處已全部改正，四字已補進 HARD 表，補後全庫硬傷仍是 0（無基準漂移），
且注入測試確認四個新字都會報紅。刻意不收「占」「里」「面」「于」等繁體本字
或兩用字，以及「吃」（opencc 會建議「喫」，但「吃掉」在繁體為正字），以免誤殺。

**教訓（比較要緊）**：先前一輪用 `zhconv` 核對簡繁，結論是「無簡體字」。
本機實測 `zhconv` 的轉換是**恆等變換**——`一个时代` 轉完仍作 `一个时代`，
`台湾` 仍作 `台湾`，兩個方向都不動。也就是說那次「驗證」根本沒有檢查任何東西，
是假的全綠，而且它查的正是同一類缺陷。往後驗字形一律用 opencc（或任何
經確認會實際改變輸出的工具），並且**先做一次注入測試**：故意放一個簡體字，
確認工具會報，才能相信它報「無」。同一個道理，本檔的 `--teeth` 已在防範
結構閘門退化成永遠綠的橡皮章，字形檢查也該有同樣的一口牙。

## 覆核工具（opencc 全庫逐字覆核）

`verify:chars-opencc`（腳本 scripts/verify_chars_opencc.py）。呢支係**覆核工具、唔係閘門**

后族、台灣、知床），硬入閘門就會逼人把誤報寫入豁免，等於把閘門改到冇牙。

opencc-python-reimplemented（本 repo 冇 pyproject，同 numpy 一樣靠本機）。
